# Atomic identity status — migration and verification

Migration: `supabase/migrations/20261031000100_atomic_profile_status.sql`. Apply only after the original empty-project schema and both historical Music migrations have been reconciled with actual hosted schema/history. Installs a service-only function with fixed empty search_path; installation changes no application rows. No hosted migration has been applied in this session.

Deployment order: approve isolated staging access, compare current schema/history and back up, install function, test with synthetic actors/targets and sessions, verify anonymous/authenticated execution denied, exercise API, then review a separate production release. The new status endpoint requires this function. Without it the route errors safely; there is no fallback to nontransactional writes. Other portal flows continue using existing schema. Do not deploy backend to customers before this prerequisite is verified.

API boundary: active platform super_admin required by Express and rechecked under database row lock. Target must be a regular profile. Self-disable and all platform-admin status mutations remain blocked; no claim of MFA-governed recovery. Status allowlist is active/disabled. Errors use safe HTTP 400/403/404/409 mappings, otherwise central 500; SQL exception details are not sent to clients.

One database transaction updates profile status, deletes portal sessions and their cascading app sessions, consumes outstanding Music launch codes by deletion, and inserts an audit event with previous/new status and revocation counts. Repeated identical requests have no duplicate audit event; concurrent calls serialize. Re-enable never restores deleted sessions. Supabase Auth refresh tokens are NOT revoked by this function: they do not confer portal access without an active profile and a fresh portal login. Review independent Supabase Auth session/recovery requirements in M3.

Tests on isolated native PostgreSQL: browser roles lack EXECUTE; concurrent identical disable calls create one event; portal/app/code records are absent after disable; re-enable retains revocation; regular actor/self-disable denied; installing function again preserves populated data; synthetic audit failure rolls back status and session deletion together. This is a populated-fixture function upgrade test, not a full hosted migration-history reconciliation or Auth/SMTP exercise.

Rollback: keep the installed compatible function, revert backend only if required, and restore no sessions by hand. A forward fix is preferred. Never restore deleted session tokens from logs/backups to undo an intentional security revocation. No data is deleted by migration installation itself; actual disable requests intentionally revoke selected user's sessions within an audited transaction.
