# Read-only GitHub delivery connector

Install 005 only after the verified Phase 2 prerequisites. No hosted schema, App, private key, webhook, or installation has been created during implementation. Tests using a mocked GitHub HTTP transport do not verify a live installation. Vercel remains disabled because no authorized project/source mapping is established.

An operator registers an organization-owned GitHub App with only repository Metadata, Contents, Pull requests, Actions and Checks READ permissions. Select only approved repositories during installation. Do not grant code/deployment/administration write access. Record the App owner, installation owner, allowed repositories, key rotation responsibility and a recovery contact. GitHub installation tokens authorize the App installation, not a project manager's personal GitHub account; project-level platform approval is therefore mandatory.

Configure server-only GITHUB_INTEGRATION_ENABLED=true, GITHUB_APP_ID and GITHUB_APP_PRIVATE_KEY (PEM, escaped newlines supported) from the approved secret manager. Do not paste a PAT/private key into Control Center forms. Integration is off unless explicitly enabled. Keys/tokens never appear in API responses, rows, logs or client JavaScript. Installation tokens are minted with read permissions and one repository for sync. Discovery tokens cover the approved installation but stay on the server. Token expiry/401s enter attention; subsequent verified retries mint a fresh token. No tokens are cached across requests.

A platform administrator opens a project and approves an installation ID. Server verifies App ID, nonsuspended installation, repository permissions and account ID. A manager can discover repositories only from the approved installation, page through results, then select a repository. The server verifies repository ID, installation permission and account ownership again at connect. Contributor/viewer members read; clients, unrelated/revoked/disabled members cannot. Disconnect cancels leases and hides retained repository observations/links. Installation revocation invalidates all matching connections.

POST /api/projects/:projectId/delivery/connections/:connectionId/sync processes at most one claimed page; repeated requests advance a durable checkpoint. A scheduler may invoke npm run github:sync to process at most 14 pages. The server never starts a hidden background worker. Each page performs installation verification, token minting, canonical metadata lookup and one bounded data request. Poll categories: commits, contributors, all PR states sorted by update, workflow runs, default-branch check runs, releases and tags. Each category scans up to ten 100-record pages per cycle; this is recent activity, not a full historical archive. Whole cycles repeat after fifteen minutes; failed pages resume their checkpoint. No inaccurate timestamp is assigned to tags/contributors: their source timestamp is unknown (epoch), while observed_at records ingestion. Requested review counts are not approvals.

Rate limits honor Retry-After/X-RateLimit reset with persisted bounded backoff. Network/5xx errors retry with exponential backoff; permission/404 or repeated failure enters attention. Manager retry cannot bypass the deadline; disconnect/reconnect and webhooks preserve it. HTTP timeouts, response-size budgets, fixed GitHub API origin, redirect rejection and record/page caps bound resource use. A scheduler must run often enough to meet the desired refresh rate; freshness is shown, not promised.

Optional webhook: configure an approved HTTPS /api/integrations/github/webhook endpoint with server-only GITHUB_WEBHOOK_SECRET. Subscribe only to push, pull_request, release, workflow_run, check_run, repository, installation and installation_repositories. Verify HMAC-SHA256 over exact raw bytes before JSON parsing. UUID delivery IDs plus hashes are durable deduplication receipts: identical delivery is acknowledged, conflicting reuse rejected. GitHub supplies no signed freshness timestamp; retain receipts to prevent replay. Webhooks queue canonical provider polling rather than trusting payloads as repository facts. Installation deleted/suspend revokes access; removed repositories fail closed on subsequent canonical permission verification. Polling works without webhook administration. Do not log webhook bodies or signatures.

Explicit task/milestone linkage accepts only persisted PR/release record IDs in the same project. It does not infer relationships by title. Original source URLs, source time and observation time remain traceable. Timeline events snapshot historical state at ingestion. No automatic production deploy, rollback or secret changes exist. Rollback: disable the connector/scheduler and forward-fix schema; preserve evidence. Operator retention/export governance remains required.

Authoritative API guidance: https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation and https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries .
