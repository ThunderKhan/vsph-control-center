# Live GitHub acceptance — explicit read-only proof

`npm run github:verify` uses the configured VSPH GitHub App, not the ChatGPT connector installation or a PAT. It does not create a project/connection, run synchronization, change code, send email or write a database. It mints temporary read-scoped installation tokens and reads the approved repository via the provider implementation.

First configure the organization-owned least-privilege App as documented in GITHUB_DELIVERY.md. Supply server-side GITHUB_ACCEPTANCE_APPROVED=true, GITHUB_ACCEPTANCE_INSTALLATION_ID, GITHUB_ACCEPTANCE_ACCOUNT_ID, GITHUB_ACCEPTANCE_REPOSITORY_ID and GITHUB_ACCEPTANCE_EXPECTED_REPOSITORY (owner/name). These identifiers must name an explicitly approved sandbox. Existing GITHUB_INTEGRATION_ENABLED, GITHUB_APP_ID and GITHUB_APP_PRIVATE_KEY are required. Never paste private keys or tokens into chat/Git.

Provider-only verification checks canonical ownership/name/IDs, then reads one page for each of seven categories. Output contains counts, states and observation digests, not source titles, private repository names, cookies, keys or raw provider bodies. providerReadsVerified means only that those live provider reads succeeded. Full application acceptance remains false.

For a staged persisted-read comparison, additionally supply STAGING_APPLICATION_ORIGIN, STAGING_PORTAL_SESSION, GITHUB_ACCEPTANCE_PROJECT_ID and GITHUB_ACCEPTANCE_DENIED_PROJECT_ID. Origin must be HTTPS (HTTP only for loopback); redirects, userinfo, paths, query and fragments are refused. Use a dedicated short-lived staging session through an approved secret mechanism. Choose an existing authorized project with an already synchronized repository, and a known existing unrelated project that this session must not access. These are explicit prerequisites, not fixtures installed by the command.

The command reads both project delivery APIs: the authorized project must return 200 with the active expected connection, and the unrelated project must return 403/404. It compares provider-normalized facts to persisted records within the fetched page intersection and requires at least one exact match and zero mismatches. Empty/stale observations fail; synchronize and reconcile first. A successful comparison is still not a complete cross-role/browser/Auth/PostgREST or deployment certification. The command does not prove that the supplied denied project exists; the operator must establish that independently.

No live command succeeded in this execution: the VSPH App key/approved installation and hosted staging identity were unavailable. Unit tests inject provider/application transports and explicitly keep fullApplicationAcceptanceVerified false. Treat those tests as command correctness evidence only. Missing approval/configuration fails without credentials or private payloads in errors. After actual staging setup, retain the report privately and complete the manual multi-role browser matrix before release approval.
