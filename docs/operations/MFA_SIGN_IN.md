# MFA-aware portal and product sign-in

Portal and second-stage product password verification use the same server-owned `verifyIdentity` service. After password verification, a fresh non-persistent Supabase client obtains the authoritative identity and current/next authenticator assurance. An enrolled verified factor cannot be ignored by the opaque portal-session flow.

For enrolled TOTP, the browser receives public factor identifiers/names only after a valid password, selects a verified authenticator when necessary, and submits its six-digit code with the password. The server lists verified factors, calls Supabase challengeAndVerify, then rechecks AAL2 and the same identity before creating a portal/product session. Client-provided assurance, metadata and unknown factor IDs confer no authority. Missing/wrong codes, unsupported enrolled methods, provider errors, missing session/assurance and identity mismatch fail closed. Existing tenant/product/account checks still apply independently.

The fresh provider verification session is signed out with explicit `scope: local` on success and incomplete/failed MFA. Default/global provider logout is prohibited. Cleanup failure also fails verification. Provider access/refresh tokens are never returned to the browser, persisted in portal storage or logged. Opaque portal cookies retain HttpOnly/SameSite/Secure policy. The UI clears one-time codes after each attempt and stores no credentials in localStorage. Existing credential endpoint Origin/body/rate-limit controls remain in force.

This increment verifies **already enrolled TOTP**; it does not enroll/unenroll factors, implement phone/passkey/recovery-code verification, reset credentials or provide administrator recovery. Unsupported enrolled methods explicitly deny password-only sign-in. No hosted Auth settings, identities or real factors were changed during implementation. No new SQL migration is required. Live provider acceptance requires an approved identity with a real enrolled authenticator and remains unverified.

Existing opaque portal sessions are not retrospectively assigned AAL2 or automatically revoked by this change. Their existing four-hour expiry/account revocation remains. A future enrollment/recovery workflow must govern those sessions; this change must not be described as full lifecycle MFA enforcement. Future privileged-action workflows must freshly verify the signed-in identity rather than trusting a previously rendered MFA form or a browser assertion.

Native PostgreSQL/HTTP acceptance checks that missing/wrong MFA creates no durable session and success produces only an opaque portal cookie, while disabled profiles still deny access. Node cases cover factor selection, unsupported/unverified factors, missing/stale assurance, provider/cleanup outages, rate limits and identity mismatches. Desktop/mobile Chromium use an explicitly isolated fake Auth provider with a native database. This test provider is imported only by test fixtures, has no production environment bypass and does not prove real Supabase Auth behavior.

Rollback: retain the security service or forward-repair it. Reverting to password-only verification reintroduces the enrolled-factor bypass and requires security review. Do not disable a real user's MFA merely to make a test pass. Existing organization/product/project permissions remain unchanged.

References: [Supabase TOTP flow and assurance](https://supabase.com/docs/guides/auth/auth-mfa/totp), [factor listing](https://supabase.com/docs/reference/javascript/auth-mfa-listfactors), [challenge and verification](https://supabase.com/docs/reference/javascript/auth-mfa-challengeandverify), [local provider sign-out](https://supabase.com/docs/reference/javascript/auth-signout). The installed SDK implementation was inspected for these calls; no dependency change is required.
