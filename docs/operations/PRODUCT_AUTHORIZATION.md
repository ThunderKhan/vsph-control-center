# Product authorization and scoped reads — M1 increment

Platform administrators manage the catalog/customer grants through /admin. They no longer inherit product staff authority or every tenant context. Operating a product requires their own explicit active organization membership and assigned product role, as for every other identity. Existing active platform sessions remain valid for central administration. A platform admin with no product assignment will see an empty tenant selector / launch denied; assign a reviewed role through existing controls before testing a product. This is an intentional least-privilege behavior change.

getContexts first queries only the signed-in user's active memberships and selected-product roles, intersects their tenant IDs, then fetches subscriptions, grants and organizations only for those IDs. At most 500 memberships/roles are supported per account; overflow fails closed rather than silently omitting a valid permission. Candidate IDs are queried in batches of 50 to bound REST URL sizes. Pagination for larger accounts remains M2 work. Active organization, enabled grant, product role, active membership, subscription effective start and unexpired end are all required.

Record creation uses explicit product allowlists. CRM: super_admin/admin/manager/user. Music portal sample records: super_admin/admin/manager/staff/user. Viewer, musician, unknown roles and platform_super_admin cannot create generic records. Music musician-specific performer workflows belong to the separate product and are not implemented here. Record tenant/actor always derive from the verified session; submitted tenant IDs confer no authority. UI capabilities mirror server rules but do not authorize writes.

Database-backed HTTP tests execute the actual Express routes/middleware against native PostgreSQL rows with a test-only query transport adapter. They cover anonymous, wrong-tenant query IDs, ordinary member, explicitly assigned platform admin, missing product role, invited/suspended membership, musician/viewer write denial, expired subscription, disabled profile and deleted portal session. The adapter is not PostgREST or Supabase Auth; real-service Auth/SMTP/staging integration remains missing. SQL constraint/RLS tests are separate.

Concurrency limitation: context checks and record mutation remain separate REST statements. Authorization is rechecked per request, but atomic revocation-versus-write ordering needs M2 database transactions. Existing sessions observe changed roles/memberships on their next request; no stale cached permission is introduced.

Migration: none; uses existing columns including starts_at. No hosted deployment performed. Manual staging: platform admin can still manage catalog, cannot open unrelated customer product, explicitly assigned staff can open its own tenant, invite pending grants nothing, expired/future plan denies access, and denied writes produce no rows. Rollback: revert code, with explicit security review because this restores implicit platform product privileges.
