# Projects MVP: installation, roles and acceptance

The established Projects schema and the November 9 additions — `20261109140000_project_custom_applications.sql`, `20261109141500_organization_only_onboarding.sql`, and `20261109143000_project_workforce_governance.sql` — are **installed on the existing configured VSPH Supabase database**. The guarded installation verified all 44 canonical ledger records, RLS/function grants and the preservation of 14 existing table fingerprints; see [exact November 9 evidence](PROJECT_NOV09_MIGRATION_INSTALL.md). Other targets are not migrated by Git merges. A new hosted backup/restore rehearsal, full live Auth/invitation and role workflow acceptance and production web-app deployment remain unverified. Do not run demo seeds, bootstrap, version-altering CLI repair or isolated browser fixtures against existing customer data.

After installation, sign in using an existing platform administrator, open Projects in the sidebar, choose New project, enter a unique uppercase key/name, select internal or customer ownership (customer requires an organization), optionally link products and dates, then create. Ownership is independent of subscriptions/product permissions. The creator is the initial accountable manager; settings can transfer ownership to another active member/manager.

In Project → Team, choose an **active internal employee with an explicitly accepted, linked portal identity**, set the project role and optional team label, and save. An ordinary project manager may assign contributors and viewers only to projects they manage; only the platform owner can appoint or remove project managers. Unlinking or deactivating an employee closes internal manager access. Removing an employee with unfinished assigned tasks is blocked until those tasks are reassigned. The accountable project owner cannot be removed without transferring ownership first. Contributors have only assigned-work privileges and their own HR self-service; viewers are read-only. Client access requires explicit membership, an active customer organization and a client-visible project. It does not confer internal HR, project-manager or reusable-product rights. Existing access remains rechecked on every server-side mutation.

Create milestones, then tasks with assignee, milestone, priority, target date and sharing. Use task state controls through todo→in_progress→in_review→done; blocked/cancel/reopen transitions are explicit. Managers can edit tasks/milestones, set dependencies, add HTTPS deliverables and comments, change team access, manage project lifecycle and archive. Finish milestones only when work/dependencies are complete; finish the project only when work is resolved. Archived projects are read-only except platform restoration. Every mutation uses a project version and commits activity/audit with data. A concurrent stale edit returns 409; refresh and reconcile.

Overview progress is completed/noncancelled visible tasks; overdue work counts unfinished task/milestone target dates. Health reports visible current blockers/overdue work, not a forecast or SLA. Empty projects do not invent percentages. Search/lifecycle filters and UUID keyset pages are server-backed. Task-state filtering is within the bounded project work set. Limits: 500 tasks, 100 milestones, 200 memberships and latest 200 comments/deliverables/events. No file upload, invoice, deployment or GitHub sync is implied.

REST: GET/POST `/api/projects`, GET `/api/projects/directory`, GET/PATCH `/api/projects/:id`; GET `/api/projects/manager-overview` (platform owner only), GET `/api/projects/:id/workforce` (authorized manager), POST `/api/projects/:id/workforce/{assign,remove,manager-grant,manager-revoke}` (role-scoped). Each assignment requires the current project version. The existing members/milestones/tasks/comments/deliverables endpoints remain. GET/POST/PATCH custom project applications are served under `/api/projects/:id/applications`, independently from reusable catalog products. Browser APIs use existing portal cookie/Origin rules; server validation and service-only Postgres RPCs enforce current identity, tenant, project role, employee link and version. Direct anon/authenticated table/RPC access remains revoked.

CI provisions an empty PostgreSQL 17 database and synthetic profiles/sessions, boots the real Express stack through the documented test SQL transport adapter, and runs desktop/mobile authenticated Playwright creation→assignment→work→evidence→reload→outsider-denial. It does not test real Supabase password/SMTP/PostgREST services. Fixture boot code is test-only and cannot be activated through production HTTP routes. No fixture/sample project records are installed by product migrations.

Ordinary-user local test commands: npm run test:db:local; npx playwright install chromium; npm run test:e2e:db. The latter provisions a disposable native database for authenticated browser fixtures; root OS execution deliberately refuses to create OS users. Alternatively point TEST_DATABASE_URL to an empty loopback vsph_test database and run npm run test:db; for browser fixtures set PROJECT_E2E_DATABASE=true and run npm run test:e2e. Do not point fixture commands at hosted staging or production. Windows-native execution was unavailable; native DB/browser evidence is from Linux CI.

Manual acceptance: sign in → Projects → create internal/customer project → add manager/developer/viewer/client → create milestone/dependency/task → assign developer → change status → comment/evidence → reload → reconcile overview/history → revoke access → verify denied → finish work/milestones → complete/archive. Repeat on mobile with drawer and horizontal table scrolling, keyboard focus and concurrent edits. Existing login/dashboard/apps/onboarding/admin routes retain regression checks. Remaining hosted Auth/SMTP/SSO, full WCAG/device matrix, restore/load exercises and larger data pagination remain explicit operational gaps.
