# Project inbox and reporting

006 requires 005 and all earlier migrations. Hosted installation has not occurred. Assignment, milestone completion, PR/release changes and build failures/recoveries append deduplicated recipient events in the same database transaction as their source. Notifications are in-app only; this implementation does not send emails, push messages or call third-party notification services.

An outbox dispatcher takes up to 50 rows with SKIP LOCKED, rechecks current active non-client project permission and preferences, then atomically inserts one inbox entry and marks delivery. Database failures persist bounded retries/backoff; after five attempts attention is visible. Each user may retry their own attention entries. GET /api/notifications dispatches only that user's eligible batch, so ordinary inbox reads make progress without an always-on process. Preferences separately control assignments, delivery/milestone changes and overdue work. Suppressed events are not replayed when preferences change. Inbox is latest 100, not an infinite archive.

A scheduler may explicitly invoke npm run notifications:dispatch: a bounded scan enqueues up to 500 overdue assigned tasks per batch/day and dispatches 50 eligible entries. Daily task/user keys prevent repeated reminders in the same UTC day. Call enough batches to drain a larger portfolio. No implicit background server starts. Milestone completion is notified; overdue milestone reminders, subscription/security notices and external channels remain future work.

Recipients never receive another project's private data. Inbox reads recheck current project permission and active repository installation/connection. Client roles never see internal project/engineering notices. Revoking membership, disabling the profile or disconnecting the source removes the corresponding entries from subsequent reads. Stored events contain identifiers, not cached private titles; display resolves currently authorized source rows. Existing rendered pages cannot erase information a user has already seen.

Project inbox and reports are available in the Projects screen disclosure. Mark entries read, change preferences, inspect queued/attention counts and retry failed internal deliveries. Reports use authorized persisted tasks, milestones and observations; filter by project ID, authorized customer/owner, project lifecycle and project creation date. Up to 100 projects are returned. Counts explicitly mean completed/total tasks, active assignments to you, overdue tasks, milestone state, retained open PRs and failed workflow/check observations. A failed historical run is not a claim that the latest branch is failing. Last sync/activity timestamps and source URLs permit reconciliation. Vercel status remains unconfigured; no uptime/productivity/forecast metrics are invented. Broader export/search, pagination, retention and notification governance remain roadmap work.

Tests cover atomic capture, duplicate delivery, preferences, read ownership, scanner deduplication, database outage retry and revoked-membership report/inbox denial. Synthetic sessions and provider fixtures do not verify hosted Auth/PostgREST or live delivery. Rollback: disable explicit batch scheduler/UI and forward-fix; do not delete audit/outbox history.
