# Durable provisioning and invitation capabilities

Migration 20261031000200 is additive and service-only. Install in isolated staging before deploying these routes. No hosted migration or real delivery was performed. Old account-wide bearer invitation links are deliberately rejected; an operator must reconcile outstanding legacy invitations.

POST onboarding requires a UUID Idempotency-Key. A transaction serializes the key, rejects changed payloads, creates one organization/subscriptions/grants/job/invitation/outbox and audit. No external Auth/email call occurs in the HTTP request. The wizard keeps the key across retries; a new submission receives a new key.

Run `node scripts/dispatch-invitations.js` explicitly only after approved provider configuration. It is never started by the server. INVITATION_DELIVERY_ENABLED=true, an HTTPS INVITATION_DELIVERY_URL, server-only INVITATION_DELIVERY_SECRET and 32-byte hex INVITATION_OUTBOX_KEY are required. The provider must honor Idempotency-Key and deliver the supplied invitation URL without logging it. Ciphertext persists pending delivery; token hashes alone persist in invitations. Retain the encryption key until queued deliveries drain. Never expose the key, ciphertext or URLs in the recovery UI/logs.

Workers use bounded leases/SKIP LOCKED, stable preallocated Auth IDs, encrypted payload reuse, bounded attempts/backoff and durable failure state. An ambiguous provider delivery retries the same idempotency key. Auth creation is an external saga, not a cross-service transaction. Database bind/profile/membership/roles are transactional. New profiles remain disabled until acceptance; existing profiles are not elevated or password-reset. Purpose is the platform-issued random 256-bit capability, bound to one invitation/membership with expiry and single-use reservation; it is not inferred from a general Supabase bearer.

New identities enroll a password through a reserved capability, then activate exactly that membership and audit atomically. Existing identities must sign into the portal and match the invited user. Password enrollment is an external Auth step: failure/uncertain completion invalidates the capability and enters requires_attention, never silently activates or blindly repeats an unknown mutation. Recovery requires the administrator to reconcile the provider first, wait out in-flight acceptance, then explicitly confirm recovery; generation/token rotation invalidates the old link. No distributed transaction or exactly-once external side-effect claim is made.

/admin/provisioning lists bounded job state and exposes retry/revoke/reconciled recovery. Sent invitations cannot be resent by a blind retry; expired/revoked invitations need a new reviewed workflow. Platform admin lifecycle, atomic mutation auditing beyond this scope, SMTP delivery verification and distributed throttling remain separate gaps.
