# Executable staging readiness — read-only

The migration manifest records exact SHA-256 hashes and explicit dependency order for bootstrap plus every registered migration. `npm run check:migrations` verifies repository content without connecting to a database. Bootstrap is never an inspection/apply command. CI runs the manifest check and a native catalog-inspection case.

Important existing history issue: both historical Music migration filenames begin with version 20261030. Native tests use an explicit ordered list, but a Supabase CLI ledger keyed by version cannot be assumed to represent both files. The inspector reports this collision and missing/unknown ledger entries. Do not rename historical files, repair migration history, replay bootstrap, or assume that matching table names prove installation. A target-specific reviewed reconciliation is required after actual history/object definitions are inspected. No automatic ledger repair or migration application is implemented.

A separate approved isolated staging target is required. Set server-side STAGING_DATABASE_URL, STAGING_DATABASE_HOST and STAGING_DATABASE_NAME to exactly that target, and STAGING_INSPECTION_APPROVED=true. The URL is read only from that dedicated variable, never DATABASE_URL or production/Supabase fallback variables. Remote connections require sslmode=verify-full; localhost fixtures may omit SSL. Credentials are not accepted as command-line arguments or printed. Supply them through an approved local environment/secret manager, not chat or Git.

Run `npm run staging:inspect` and preserve its JSON output privately. It begins a READ ONLY transaction with statement/lock/idle timeouts, inspects fixed catalog objects, then rolls back. It checks required table existence/RLS and browser table/column grants; service-only function signatures, security-definer/fixed search path/execute grants; session public IDs; and migration history. It returns a target fingerprint and definition hashes, never raw function bodies, credentials or customer rows. Exit 1 means a blocker, not a failed migration. Missing target/approval or mismatched host/database fails before connecting.

Catalog checks are only a prerequisite: releaseReady is always false. Inspection does not certify complete schema equivalence, backup/restore, hosted Auth/PostgREST, provider access or production release. After read-only target reconciliation, a separate approved operation must take/verify backups, rehearse missing migrations on isolated staging, validate restoration and run actual Auth/PostgREST acceptance. No hosted inspection, backup, restore or migration was possible in this execution because no approved target/credentials were supplied.

The available GitHub connector installation belongs to ChatGPT and is not the VSPH App. Its ability to read repositories does not provide the application private key or prove VSPH runtime permissions. Supabase is available as an optional connection but was not connected at the time of this readiness work.
